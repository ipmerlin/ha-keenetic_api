# Keenetic API: модемы и KeeneticOS 5.2

Форк [malinovsku/ha-keenetic_api](https://github.com/malinovsku/ha-keenetic_api).
История и лицензия MIT исходного проекта сохранены. Стабильная версия **1.3**.

## Иконка типа сети

Значок датчика «Тип сети» меняется по данным модема: 2G, 3G, 4G, 5G,
HSPA и HSPA+. Известные обозначения GSM/GPRS/EDGE, UMTS/WCDMA,
LTE/LTE-A и NR5G отображаются соответствующим поколением сети.
Неизвестная технология — `radio-tower`, отсутствующие данные — `signal-off`.
Текст показания и идентификатор сущности сохраняются.

## Динамические иконки сигнала

Для RSSI, RSRP, RSRQ и SINR используется одна шкала от нуля до четырёх
полосок. Четыре полоски — `mdi:signal`, от одной до трёх —
`mdi:signal-cellular-1/2/3`, ноль — `mdi:signal-cellular-outline`.
Отсутствующие данные — `mdi:signal-off`, без подмены нулём.
Это визуальная шкала интеграции; каждый показатель оценивается отдельно.

| Показатель | 4 полоски | 3 полоски | 2 полоски | 1 полоска |
| --- | --- | --- | --- | --- |
| RSSI, dBm | > -65 | > -70 | > -85 | > -100 |
| RSRP, dBm | > -85 | > -95 | > -105 | > -115 |
| RSRQ, dB | > -10 | > -15 | > -20 | > -25 |
| SINR, dB | > 20 | > 13 | > 9 | > 0 |

Выбирается первый подходящий столбец слева; ниже всех порогов — ноль
полосок. Пороги не являются оценкой скорости соединения.
Дополнительный YAML не нужен. Идентификаторы датчиков сохраняются.

## Устранение дублей в 1.2.5b5

Если интерфейс уже имеет штатные датчики трафика, скорости и подключения,
новые модемные датчики не дублируют их. Существующие имена и идентификаторы
сохраняются. Удаляются только повторные записи, созданные в b4, для которых
найден исходный датчик той же записи интеграции. История в базе не удаляется.
На ретрансляторах, где штатных интерфейсных датчиков нет, модемные счётчики,
скорости и подключение сохраняются. Новые показатели сигнала и сети остаются.

## Данные подключённых модемов в 1.2.5b4

Для каждого модема автоматически создаются датчики:

- модель с атрибутами производителя, прошивки и интерфейса;
- оператор, тип сети, состояние SIM и диапазон;
- RSSI и RSRP в dBm, RSRQ и SINR в dB, температура;
- полученный/отправленный трафик и входящая/исходящая скорость;
- подключение и роуминг.

Поддерживаются модемы маршрутизатора, ретранслятора и представление модема
на контроллере Wi-Fi-системы (`MwsMobile`). Данные берутся из `show/interface`
и `show/interface/stat`: команды настройки модема и AT-команды не отправляются.
Каждая запись HA показывает модемы, которые видит соответствующий Keenetic;
один физический модем может отображаться и у ретранслятора, и у контроллера.

Названия содержат интерфейс (например, `UsbQmi0`), поэтому несколько модемов
не смешиваются. Новые модемы и появившиеся дополнительные поля обнаруживаются
при очередном обновлении без перезапуска HA. Отсутствующие поля показываются
как неизвестные, исчезнувший интерфейс — как недоступный. Нулевые значения
сигнала и скорости сохраняются. Счётчики трафика сбрасываются вместе с
интерфейсом/роутером; это не биллинг оператора.

IMEI, IMSI, ICCID, телефонный номер и серийный номер SIM/модема не включаются
в новые сущности. Полный снимок API больше не записывается в отладочный журнал
координатора. Некоторые показатели зависят от модема и прошивки.

Структура данных сверена с реальным Hero 4G и контроллером Viva на 5.2 Beta 1.
50 тестов проверяют обнаружение, отключение, значения, единицы трафика,
отсутствующие поля, авторизацию, сессии и динамические иконки.
На Home Assistant 2026.10.2 проверены четыре устройства, модемы Hero и Viva,
шкала 0–4 полоски, значок 4G и устранение пяти дублей (124 → 119 объектов).

## Дополнительные исправления 1.2.5b4

При сбое настройки используется `detach()`, чтобы не закрывать общий HTTP-коннектор
Home Assistant; сервис для незагруженной записи выдаёт понятную ошибку вместо
`KeyError`. Вход NDW4 использует объявленный роутером путь, проверяет его
принадлежность тому же роутеру, принимает строковые параметры Argon2 и отдельно
сообщает об отказе первого этапа до проверки пароля. Cookie обрабатывает обычный
`aiohttp.CookieJar`, как в рабочей 1.2.5b3.

При проверке 21.10.2026 устройства с 5.2 Beta 1 успешно загрузились на 1.2.5b3
после перезагрузки записей. Причина предшествовавшего отказа первого POST
не установлена; изменения b4 не следует считать подтверждённым исправлением
этого временного отказа.

## Исправление invalid_auth в 1.2.5b3

В 5.2 веб-вход изменился: вместо старого MD5/SHA-256 используется трёхэтапный
`x-ndw4-interactive` на Argon2id и HMAC-SHA3-512. Версия 1.2.5b3 выбирает его
автоматически по ответу `/auth`, проверяет подпись роутера и сохраняет cookie.
Вычисление Argon2 выполняется вне основного цикла Home Assistant. Старый вход
сохраняется для прошивок, которые не объявляют x-ndw4. При ошибке x-ndw4 отката
на старый протокол и повторных попыток с тем же паролем нет.

**Если после ввода токена в 1.2.5b2 появилась invalid_auth:** обновитесь до
1.3, перезапустите Home Assistant, откройте меню записи Viva →
**Перенастроить**, отметьте **Удалить сохранённый токен** и отправьте форму.
Пустой пароль сохранит прежний. При необходимости логин и пароль можно заменить
в этой же форме. Удаляется только значение токена из записи HA; сам токен на
роутере не отзывается. Роутер и сущности удалять не нужно.

Токены `X-NDMA-TKN` подтверждены источниками для внутреннего RCI
`127.0.0.1:79`. Работа этого заголовка через LAN веб-сервер не подтверждена.
Для доступа Home Assistant по сети рекомендуется новый парольный вход.
Ошибки 401/403 токена и ошибки протокола теперь показываются отдельно.

Протокол сопоставлен с исходным кодом
[AWG Manager](https://github.com/hoaxisr/awg-manager/blob/main/internal/auth/ndw4.go);
атрибуция и лицензия MIT находятся в `LICENSES/awg-manager-MIT.txt`.

## Что исправлено

- Необязательный токен доступа KeeneticOS 5.2 вместо логина и пароля.
- Заголовок `X-NDMA-TKN` в запросах к API и при скачивании резервных копий.
- При заданном токене старый вход через `/auth` не вызывается; при отказе токена
  переключения на пароль нет. Токен не добавляется в URL или сообщения журнала.
- Перенастройка токена существующей записи без удаления устройств и сущностей,
  в том числе когда интеграция не загрузилась из-за ошибки авторизации.
- Проверка подключения и идентификатора роутера перед сохранением нового токена.
- Обработка отсутствующих данных о версии прошивки и необязательных release notes.
- Актуальный импорт `ScannerEntity` для Home Assistant.

## Установка через HACS

Добавьте `ipmerlin/ha-keenetic_api` как пользовательский репозиторий категории
«Интеграция». В меню репозитория обновите информацию и выберите **v1.3**.
Показ предварительных выпусков для стабильной версии не требуется.
HACS скачивает интеграцию из исходников: поддерживаются и теги, и ветка main.
`keenetic_api.zip` в Releases остаётся для ручной установки.

Если в ошибке скачивания указано `3135b87`, HACS ранее выбрал коммит ветки,
используя старую настройку ZIP-релизов. Обновите информацию репозитория и
выберите v1.3 заново; удалять запись роутера из Home Assistant не требуется.

## Установка и ввод токена

Требуется Home Assistant 2026.10 или новее. Сделайте резервную копию текущей
папки `/config/custom_components/keenetic_api` перед заменой.

1. Скачайте `keenetic_api.zip` из стабильного выпуска этого форка.
2. Распакуйте содержимое архива в `/config/custom_components/keenetic_api/`:
   файл `manifest.json` должен находиться непосредственно в этой папке.
3. Перезапустите Home Assistant.
4. Откройте **Настройки → Устройства и службы → Keenetic API**.
5. В меню нужной записи роутера выберите **Перенастроить** (Reconfigure).
6. Для подключения по сети используйте логин и пароль. Если ранее вводили токен,
   отметьте **Удалить сохранённый токен**. Пустой пароль сохранит прежний.
   Данные сохраняются только после успешного подключения; запись перезагрузится.

Пустое поле при перенастройке сохраняет действующий токен. Отметка
**Удалить сохранённый токен** возвращает вход по ранее сохранённым логину и паролю.
При добавлении нового роутера поле токена также доступно; если оно заполнено,
пароль можно оставить пустым. Создавайте отдельный токен для Home Assistant.
Не публикуйте его и не прикладывайте файл `.storage/core.config_entries` к обращениям.
Поле ввода скрыто, но токен хранится в настройках HA, как и пароль интеграции.
Используйте HTTPS при доступе через недоверенную сеть.

Для HACS добавьте **этот форк** как пользовательский репозиторий категории
«Интеграция». Не используйте одновременно
две установки одного домена `keenetic_api`: форк заменяет исходную интеграцию.

## Проверки и ограничения

Локальные тесты проверяют настоящий код клиента и шага перенастройки с подставными
HTTP-ответами и объектами Home Assistant. Проверены заголовок токена, ошибки 401/403,
отсутствие переключения на пароль, сохранение старых данных при отказе,
проверка идентификатора, старый парольный вход и отсутствующие версии прошивки.

Для тестов установите `argon2-cffi>=25.1.0` и `aiohttp>=3.12.0` в отдельное
окружение, затем выполните `python -B -m unittest discover -s tests -v`.
Новый вход проверяется настоящим HTTP-клиентом против локального сервера:
проверка proof на стороне сервера, три этапа, cookie, неверный пароль,
неизвестный логин, подмена серверной подписи, некорректные параметры и отказ
последнего этапа. Ни в одном тесте реальные пароли или токены не используются.

На 21.10.2026 парольный вход и загрузка записей проверены на реальных
устройствах с KeeneticOS 5.2 Beta 1, а совместимость со старой прошивкой —
на отдельном устройстве. В HA 2026.10.2 проверены показания модемов Hero/Viva,
динамические иконки и сохранение исходных entity_id после удаления дублей.
Другие поколения сети проверены тестами; на живом модеме наблюдалась 4G.
Подключение по токену через LAN, обновление прошивки средствами интеграции
и скачивание настоящей резервной копии роутера остаются непроверенными.
Отказ токена не доказывает неверное значение токена.
Форма сначала читает `/rci/show/version`, затем обычные данные интеграции.
Настройки роутера при проверке подключения не изменяются.

# 🧠 Интеграция Home Assistant для роутеров Keenetic

Интеграция для Home Assistant, которая предоставляет полный контроль и мониторинг вашего роутера Keenetic через его API. Превратите ваш роутер в умное устройство с широким набором сенсоров, переключателей и сервисов.

## ✨ Возможности

Интеграция создает множество сущностей для полного управления роутером:

### 📊 Мониторинг системы
*   **Сенсоры:** Загрузка CPU и памяти, время работы (uptime), WAN IP-адрес, температура чипов 2.4 ГГц и 5 ГГц, количество клиентов Wi-Fi.
*   **Бинарный сенсор:** Общий статус роутера.

### 🌐 Управление сетью и интерфейсами
*   **Трекер устройств:** Отслеживание подключенных клиентов.
*   **Сенсоры интерфейсов:** Скорость загрузки/выгрузки, объем переданных данных, время включения.
*   **Бинарные сенсоры:** Статус подключения интерфейса.
*   **Переключатели:** Включение/отключение интерфейсов.

### ⚙️ Управление функциями роутера
*   **Кнопка:** Перезагрузка роутера.
*   **Переключатели:** Управление питанием USB-портов, доступом к веб-конфигуратору, пробросом портов.
*   **Селектор:** Выбор политики для клиента.
*   **Обновление:** Проверка и установка обновлений прошивки.

### 🖼️ Прочее
*   **Изображение:** Генерация QR-кода для вашей Wi-Fi сети.

### 🔧 Сервисы
*   `keenetic_api.request_api`: Прямой запрос к API роутера для расширенного управления.
*   `keenetic_api.backup_router`: Создание резервной копии конфигурации.

## 📦 Установка

### Рекомендуемый способ: Через HACS

1.  Откройте **HACS** в вашем Home Assistant.
2.  Перейдите в раздел **Интеграции**.
3.  Нажмите на кнопку с тремя точками в правом верхнем углу и выберите **Пользовательские репозитории**.
4.  Вставьте URL этого репозитория: `https://github.com/ipmerlin/ha-keenetic_api`
5.  Выберите категорию **Интеграция** и нажмите **Добавить**.
6.  Теперь в магазине HACS найдете интеграцию **Keenetic API** и нажмите **Загрузить**.
7.  **Перезагрузите** сервер Home Assistant.

### Альтернативный способ: Ручная установка

1.  Скачайте последнюю версию архива со вкладки [Releases](https://github.com/ipmerlin/ha-keenetic_api/releases).
2.  Распакуйте содержимое архива.
3.  Скопируйте папку `keenetic_api` в директорию `config/custom_components` вашего Home Assistant.
4.  **Перезагрузите** сервер Home Assistant.

## ⚙️ Настройка

1.  После перезагрузки перейдите в **Настройки** -> **Устройства и службы**.
2.  Нажмите кнопку **Добавить интеграцию** и найдите **Keenetic API**.
3.  Следуйте инструкциям мастера настройки:
    *   **Хост/IP:** Адрес вашего роутера Keenetic (например `http://192.168.1.1` или `https://myrouter.local`).
    *   **Учетные данные:** Имя пользователя и пароль администратора роутера.
4.  После успешного добавления вы можете выбрать, какие объекты создавать, в дополнительных настройках интеграции.

## 🔌 Использование сервисов

### Сервис `keenetic_api.request_api`

Универсальный сервис для выполнения прямых запросов к API роутера Keenetic. Позволяет использовать любую команду, доступную через `/webcli/rest`. Результат возвращается в панели разработчика и может быть использован в автоматизациях и шаблонах.

**Параметры сервиса:**

| Параметр | Обязательный | Описание | Пример |
| :--- | :--- | :--- | :--- |
| `device_id` | Нет | ID устройства роутера в Home Assistant. | `router_keenetic_1234` |
| `entry_id` | Нет | ID записи интеграции в Home Assistant. | `1234567890abcdef` |
| `method` | **Да** | HTTP-метод (`GET`, `POST`, `PUT`, `DELETE`). | `POST` |
| `endpoint` | **Да** | Конечная точка API. | `/rci/show/interface/WifiMaster0` |
| `data_json` | Нет | Данные для отправки в формате JSON. | `{"show": {"system": {}}}` |

**Пример вызова через YAML:**
```yaml
service: keenetic_api.request_api
data:
  device_id: router_keenetic_1234
  method: POST
  endpoint: /rci/
  data_json: {"show": {"system": {}}}
```

## 🧩 Создание кастомных сенсоров

С помощью сервиса `keenetic_api.request_api` можно создавать собственные сущности на основе шаблонов ([Template platforms](https://www.home-assistant.io/integrations/template/)).

**Пример создания сенсора загрузки канала Wi-Fi:**

```yaml
template:
  - trigger:
      - platform: time_pattern
        seconds: "/30"
    action:
      - service: keenetic_api.request_api
        data:
          device_id: my_device_id_keenetic
          method: POST
          endpoint: /rci/
          data_json: {"show": {"interface": {"channel-utilization": {"chart": {"name": "WifiMaster0", "detail": 0}}}}}
        response_variable: r
    sensor:
      - name: "Channel Utilization WifiMaster0"
        unique_id: "channel_utilization_wifimaster0"
        state: >
          {{ r.response.show.interface['channel-utilization'].chart.data[-1].v.load }}
        unit_of_measurement: "%"
```
